> **Early-stage project.** Fluid Island is currently in the planning and exploration phase. The repository is a starting point for the project identity and collaboration; it does not yet contain a working application.

## About

Fluid Island is an open-source project exploring an adaptive, glanceable interface for Linux desktop activity.

The idea is simple: a small, unobtrusive presence on the desktop that can expand when something needs attention, present useful controls or information, and settle back when it does not. It should be able to represent many kinds of activity rather than being limited to a single feature.

The project takes inspiration from the interaction concept popularized by Apple's Dynamic Island, while aiming to become a distinctly Linux-native experience with its own design, implementation, and integrations.

## Design direction

- **Quiet by default.** The interface should not constantly compete for attention.
- **Fluid, not flashy.** Motion should communicate state changes and remain responsive.
- **Broadly useful.** Activities may include media, notifications, downloads, timers, connectivity, and future integrations.
- **Native to Linux.** Desktop integration and compatibility matter as much as appearance.
- **Reliable first.** Performance, accessibility, predictable behavior, and easy recovery take priority over visual effects.
- **Open source by design.** Development should be transparent and welcoming to community contributions.

## Illustrative branding

The current visual direction is intentionally minimal: a dark desktop surface, a soft pill-shaped island, and a small activity indicator. It is only a placeholder to communicate the idea—not the final logo or application UI.

See [`branding/`](branding/) for the editable SVG concept and brief.

## Status

**Planning / prototype exploration.** No supported desktop environments, installation methods, or feature guarantees have been announced yet. Technical choices will follow repository research and measured prototypes rather than being locked in prematurely.

## Roadmap direction

- [ ] Audit related open-source projects and licenses.
- [ ] Define the first supported desktop environment and integration boundary.
- [ ] Prototype the core activity surface and state transitions.
- [ ] Establish performance, accessibility, and reliability baselines.
- [ ] Document installation, configuration, and contribution workflows.
- [ ] Add activity integrations incrementally.

This is a directional checklist, not a release schedule.
